# 仓库模块开发

适用版本：Backup-fang523 1.0.0；仓库接口版本：1；运行环境：Windows x64、.NET Framework 4.8。

本文描述当前源码的实际接口。README 由项目维护者单独维护。

## 1. 安装与源码结构

正常执行项目根目录的 `build-ui.ps1`，会同时构建主程序和四种内置仓库模块：

```text
安装目录/
├─ Backup.exe                         界面、仓库会话管理
├─ Backup.exe.config                  包含 repositories 的程序集搜索路径
├─ Backup.Core.dll                    模块接口、刷新缓存、队列、数据库和备份规则
├─ repositories/
│  ├─ local/
│  │  └─ Backup.Repository.Local.dll   本地文件系统
│  ├─ smb/
│  │  └─ Backup.Repository.Smb.dll     SMB / Windows 网络路径
│  ├─ webdav/
│  │  └─ Backup.Repository.WebDav.dll  WebDAV，包含 OpenList 可选优化
│  └─ sftp/
│     ├─ Backup.Repository.Sftp.dll    SFTP
│     ├─ Renci.SshNet.dll              SFTP 依赖
│     └─ …                            SFTP 其他依赖及其许可说明
└─ …                                 原有数据、缓存、原生库等
```

发布时应复制整个 `build` 目录，包含 `repositories` 子目录。不要只复制 EXE。模块只在进程中发现一次，添加或替换 DLL 后需要重新启动软件。目录中放置的是可执行程序模块，只安装可信来源的模块。

日常开发仍修改下表中各类型的源码，再运行 `build-ui.ps1`；脚本会自动生成对应模块及上述安装目录结构。源码作为开发入口，DLL 作为编译结果，连接、刷新缓存和传输管理仍由主程序与 Core 统一负责。

从 0.14.72 的平铺模块布局更新时，用新 `build/repositories` 整个替换安装目录原有的 `repositories` 文件夹。新版只在它的第一层子文件夹中发现模块入口；根目录残留的旧 DLL 不再参与加载，模块入口不进行更深层递归搜索。仓库数据目录和数据库路径不受此安装布局调整影响。

源码对应目录：

| 目录 / 文件 | 职责 |
| --- | --- |
| `src/Backup.Core/RepositoryModules.cs` | 公开接口、模块发现、描述信息、通用路径检查 |
| `src/Backup.Desktop/RepositoryConnections.cs` | 按仓库和凭据复用根会话，分配目录视图，汇总连接状态 |
| `src/Backup.Core/DirectoryRefreshCache.cs` | 目录元数据缓存、并发请求合并、刷新间隔 |
| `src/Backup.Desktop/RepositoryRuntime.cs` | 将已提交的读写结果更新到本地列表和状态 |
| `src/Backup.Core/VolumeUploadScheduler.cs` | 统一上传和下载调度 |
| `src/Backup.Core/LocatedBackupDestination.cs` | 新文件布局、已登记位置、放错目录的旧文件查找 |
| `src/Backup.Repositories.Local`、`Smb`、`WebDav`、`Sftp` | 各类型模块入口和协议实现 |
| `src/Backup.Repositories.FileSystem` | 本地和 SMB 共用的实现源码，分别编译进两个模块，无相互依赖 |
| `src/Backup.Repositories.Shared/AssemblyInfo.cs` | 内置模块版本 |
| `work/BuildRepositoryModules.ps1` | 内置模块构建步骤，由 `build-ui.ps1` 调用 |

原 Core 下部分旧驱动文件只保留源码迁移位置注释，便于增量包覆盖原文件；实际协议实现只编译在对应模块中。Core 和 Desktop 均不引用具体内置驱动程序集。

## 2. 新模块的接入方式

创建一个以 `Backup.Repository.` 开头的类库，例如 `Backup.Repository.MyStorage.dll`，引用当前发行版的 `Backup.Core.dll`。提供至少一个公开、非抽象、具有公开无参构造函数的 `IRepositoryModule` 实现。

模块描述必须满足：

- `ApiVersion` 为 `1`。
- `Protocol` 是稳定且唯一的小写标识，只能包含 `a-z`、`0-9`、`-`。该标识会保存在仓库配置中，发布后不要随意修改。
- `local`、`smb`、`webdav`、`sftp` 是内置模块保留标识。扩展使用自己的标识。
- `DisplayName` 用于添加、编辑仓库时的驱动选择。
- `PathKind` 为 `FileSystem` 或 `Uri`；URI 类型必须声明支持的 `Schemes`，例如 `https`。地址不能包含明文账号密码、查询串或片段。
- `Authentication` 为 `None`、`Password` 或 `Ssh`。主程序提供账号密码、SSH 私钥输入和 Windows 用户级凭据加密；模块不要自行明文保存密码。

为每个模块建立一个独立子文件夹，例如 `repositories/my-storage/`，将模块 DLL 及其私有依赖放在同一文件夹，重新启动后，主程序自动发现新类型并显示在驱动列表中。无需修改或重新编译主程序。依赖 DLL 避免使用 `Backup.Repository.*.dll` 命名，防止被当作模块入口扫描。模块文件夹名可自定，建议采用简短英文名称。

加载失败、接口版本错误或协议冲突会写入软件的可复制日志。不会覆盖已经加载的其他协议；使用未加载类型时，会明确报告缺少模块。

## 3. 模块入口与根会话

```csharp
public interface IRepositoryModule
{
    int ApiVersion { get; }
    RepositoryModuleInfo Info { get; }
    IManagedBackupDestination Create(
        string id, string location, RemoteConnectionOptions options);
}
```

`Create` 返回值的 `Id` 必须等于传入仓库 ID，并且必须实现 `IRepositorySession`。构造模块、读取描述信息和创建会话都应延迟网络连接，不得在发现模块时扫描仓库。

```csharp
public interface IRepositorySession : IManagedBackupDestination, IDisposable
{
    string ConnectionState { get; }
    string ConnectionError { get; }
    event Action ConnectionStateChanged;
    IManagedBackupDestination ForDirectory(
        string location, CancellationToken cancellation);
    void ShareDirectoryRefresh(
        DirectoryRefreshCache cache, string credentialScope);
    IList<StorageEntry> ListEntriesAt(
        string location, CancellationToken cancellation, bool fresh);
}
```

根会话由主程序保留和释放。`ForDirectory` 只返回当前仓库根目录或其子目录的适配器；释放这个目录适配器不能关闭共享根会话或其他正在上传、下载的连接。目录适配器拥有自己的取消令牌和临时上传状态，不得用修改共享根会话令牌的方式切换操作。

连接状态沿用 `空闲`、`正在连接`、`已连接`、`连接失败`，错误说明放入 `ConnectionError`。仅在状态实际变化时触发事件。本地文件系统没有持续连接时可返回空字符串。

远程连接沿用统一策略：连接 60 秒、普通操作 120 秒、空闲连接 600 秒、SFTP 保活 30 秒。上传响应采用现有分阶段处理，不能用普通操作超时截断仍在正常处理的上传。

## 4. 最小可编译接入示例

以下示例复用本地模块，增加一个独立协议类型，演示发现、驱动选择及统一管理的接入方式。它不是新的网络协议实现；从零实现协议时，应返回自己的 `IRepositorySession`。

将以下代码保存为 `MyStorage.cs`：

```csharp
using Backup.Core;

public sealed class MyStorageModule : IRepositoryModule
{
    private static readonly RepositoryModuleInfo description =
        new RepositoryModuleInfo(
            "my-folder", "示例文件夹仓库",
            RepositoryPathKind.FileSystem,
            RepositoryAuthentication.None);

    public int ApiVersion { get { return 1; } }
    public RepositoryModuleInfo Info { get { return description; } }

    public IManagedBackupDestination Create(
        string id, string location, RemoteConnectionOptions options)
    {
        return RepositoryModules.Require("local").Create(id, location, options);
    }
}
```

在 Windows PowerShell 中编译，`$app` 指向已构建的程序目录，`$source` 指向上述源码：

```powershell
$app = 'C:\path\to\build'
$source = 'C:\path\to\MyStorage.cs'
$moduleDir = Join-Path $app 'repositories\my-storage'
New-Item -ItemType Directory -Path $moduleDir -Force | Out-Null
$compiler = Join-Path $env:WINDIR 'Microsoft.NET\Framework64\v4.0.30319\csc.exe'
& $compiler /nologo /codepage:65001 /target:library /platform:x64 /optimize+ `
  ('/r:' + (Join-Path $app 'Backup.Core.dll')) `
  ('/out:' + (Join-Path $moduleDir 'Backup.Repository.MyStorage.dll')) `
  $source
if ($LASTEXITCODE -ne 0) { throw '模块编译失败' }
```

重新启动软件，“驱动”中会出现“示例文件夹仓库”。只添加扩展不需要重编译主程序或 Core。

## 5. 文件读写接口

`IManagedBackupDestination` 定义基本操作：

| 操作 | 约定 |
| --- | --- |
| `PrepareWrite()` | 在确实开始写入时准备当前目录，不承担全仓扫描或数据库同步 |
| `OpenTemporary(name)` | 返回当前文件的临时写入流；不能覆盖已有正式文件 |
| `CommitTemporary(name)` | 提交本次上传，只允许同一目录内的提交或改名 |
| `DeleteTemporary(name)` | 只删除有精确所有权记录的本次临时文件 |
| `Stat(name)` | 返回文件名、是否存在、长度；无权访问、超时、结果不明确必须抛错，不能假装不存在 |
| `OpenRead(name)` | 读取指定文件；校验、恢复和修复规则由主程序组织 |
| `DeleteObject(name)` | 删除明确指定的单个对象，不扩大删除范围 |

根据支持能力实现以下接口；现有完整功能的仓库应提供前七项：

| 接口 | 用途 |
| --- | --- |
| `ICancellableBackupDestination` | 操作取消令牌，停止时中止本次读写 |
| `IBandwidthDestination` | 使用统一限速和本机流量统计 |
| `IOwnedUploadDestination` | 临时文件所有权日志与确认后的释放 |
| `IReadOnlyDestinationProbe` | 只读连接检查，不能顺便新建根目录 |
| `IStorageDirectoryListing` | 只列当前一层目录，返回 `StorageEntry` 的名称、位置、类型和大小 |
| `IStorageEntryRemoval` | 仓库视图指定条目的检查和删除 |
| `ITaskStorageRemoval` | 删除已明确指定的整个任务目录，不能删除其他任务目录 |
| `IKnownLengthUploadDestination` | 上传前提供准确长度，适用于需要 Content-Length 的服务 |
| `IRangedBackupDestination` | 单文件多段下载；不支持 Range 时准确返回降级信息 |
| `ITemporaryUploadProbe` | 查询本次持有的临时对象 |
| `IInterruptedUploadDestination`、`IRecoverableUploadDestination` | 延续精确登记的同一上传所有权，不得猜测别的临时文件 |
| `IAbandonedUploadDestination` | 查询正式对象、放弃原临时上传 |
| `IBackgroundUploadProgress` | 服务端后台任务的状态和进度 |
| `IRemoteFolderBrowser` / `ICancellableRemoteFolderBrowser` | 可选的远程目录选择能力 |

当前 WebDAV、SFTP 的文件夹选择器保留原有交互；新增 URI 类型可直接输入完整仓库地址并进行只读连接检查。需要特有配置或专用文件夹选择器时应另行扩展界面，不应把这类交互隐藏在普通上传操作里。

公共辅助类 `UploadStaging` 负责临时名和精确所有权，`BandwidthStream.Wrap` 负责限速、实际字节统计和取消。驱动不能在外面再次累计同一批字节。内置模块的友元访问用于复用已有内部实现，不是扩展模块的必需条件；第三方模块应使用公开接口。

## 6. 统一刷新和调度

主程序向根会话传入共享的 `DirectoryRefreshCache` 与凭据范围。所有目录视图必须复用它，不能各自启动定时扫描。

```csharp
// cache、scope 由 ShareDirectoryRefresh 传入；location 是当前目录。
if (fresh) cache.InvalidateFolder(location);
return cache.Read(
    scope, location, false,
    () => ReadExactlyOneDirectory(location, cancellation),
    cancellation);
```

`ReadExactlyOneDirectory` 是驱动自己的单层目录查询，不可再次调用上述缓存入口造成递归等待。WebDAV 在原生 OpenList 列表和 DAV 列表之间共享同一个缓存，并区分原生查询结果。

当前管理规则：

- 同一凭据范围、同一目录的查询合并为一个进行中的请求。
- 成功查询的最短刷新间隔为 2 秒；失败查询的重试间隔为 20 秒。`fresh` 使结果失效，但不绕过最短请求间隔。
- 缓存只保存元数据，最多保留 64 个空闲目录条目；不保存文件内容，不代表永久成功状态。
- 上传、删除等已提交结果通过主程序更新本地列表并使对应目录缓存失效，不触发全仓遍历。
- 仓库浏览只读取当前选中的仓库和当前目录。切换选择后，已经开始的读取继续完成，连接按既有空闲规则保留，不扩大读取范围。
- 明确点击全仓完整性检查时才遍历所有目标，最多并发检查 8 个仓库。
- 上传由统一队列管理：总计 5 路，同一仓库最多 3 路；下载总计最多 16 路，多个仓库、文件和单文件分段共用此上限。
- 驱动不能另起一套不限量的上传、下载或递归扫描队列。`ForDirectory` 不负责决定传输并发。

普通目录驱动在完成实际写入或删除后，也应使其当前目录缓存失效；不确定是否成功时保留不确定状态，交由既有核对流程处理。

## 7. 需要保持的备份和恢复语义

这些规则属于 Core / 主程序，不由各个仓库重复实现：

1. 新写入数据使用 `data-任务代号/编号目录`，版本库使用 `node-任务代号/编号目录`，主数据库快照在仓库根目录。驱动只操作收到的当前目录和文件名，不自行移动已有备份包。
2. 已有文件可能被用户放错目录。恢复或实际修复可按名称和大小查找；需要读取内容时才校验哈希。普通列表、完整性检查不能为“校验”而下载数据包。
3. 检查根据仓库文件和待备份清单修正本地数据库；修复根据本地登记状态操作仓库。检查不修复、不删除、不同步数据库。修复仅在确实发生改动后同步数据库。
4. 已登记但本地缺少的版本数据库允许按原规则下载；用户明确删除的版本不能被重新导入。
5. 临时连接失败、列表刷新延迟、目录创建结果不明确，都必须保留原目标继续核对。已经使用过的仓库根目录暂时查不到时，不得自动重建；不明确的创建请求不能重复提交。
6. 上传成功依据正式对象的名称和大小，以及既有服务端任务判定。不能仅凭本机发送结束、HTTP 200 或服务端进度 100% 就认定正式文件已发布。
7. 核对仍为每 20 秒一次、三次核对后进入既有三次重新上传规则；运行或排队中的 OpenList 任务按现有规则继续等待。驱动不能再额外叠加一套自行重传规则。
8. 不发送跨目录的远程移动、复制命令。仅允许本次上传在同一目录内提交正式文件。仓库路径迁移使用既有下载、上传和确认流程。
9. 停止、立即停止和关闭软件按现有取消与所有权清理规则处理。无有效完整引用的未完成包不能登记为成功备份；正式文件已成功的部分按既有规则核对后保留。
10. 无变化的任务立即完成，不创建版本、不上传或同步数据库。模块不能把连接探测、目录扫描或预先上传数据库插入任务开始过程。

## 8. OpenList 可选能力

普通 WebDAV 与 OpenList 仍属于同一个 WebDAV 模块。模块通过 `IOpenListRepositoryModule` 提供服务识别和授权，通过 `IOpenListRepositorySession` 接入授权更新、无优化回退和诊断事件；后台任务记录保留在主数据库中。

其他仓库不需要实现这两个接口。已存在的 OpenList 2FA、令牌共享、5 分钟未输入后的普通 DAV 回退、已提交文件继续核对、授权恢复等规则均由既有管理流程负责。不要将账户令牌复制到另一个服务地址。

## 9. 提交模块前的验证

建议使用独立本地目录或模拟服务，至少覆盖：

- 仅放入扩展 DLL 后即可发现类型，主程序不需要重编译。
- 初次备份、无变化再次备份、历史版本恢复、重新启动后恢复，内容一致。
- 正确处理同名不同大小、缺失、权限错误、超时和不完整目录响应。
- 多个相同目录请求只产生一次查询；不同凭据、仓库、目录不会混用结果。
- 检查完整性只读取元数据；修复只执行已确认需要的操作。
- 文件放错目录后能按名称和大小识别；新补传仍写入规范目录。
- 停止时取消当前读写，不误删其他任务、其他仓库或正在上传的对象。
- 替换、删除和版本清理后，列表及数据库状态一致。
- Range 不支持、部分响应、最后一段缓慢、取消下载，都能按统一下载接口正确处理。
- 模块缺失、协议冲突和接口版本不兼容时，有明确诊断，其他可用模块仍能使用。

扩展模块只需交付其 DLL、必要依赖、对应源码与许可说明。不要把测试仓库、测试数据库、真实账户或运行日志放入发布包。
